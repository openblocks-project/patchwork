# Catalogue branch and CI (P4.3.4)

The public catalogue is the **`catalogue` branch** of the Patchwork
repository, with no server behind it. It is an orphan branch: it has no
history in common with the application, and the two are never merged into
each other.

| Branch | Holds |
|---|---|
| `main` (default) | the stable application, and the trusted Submission paths guard |
| development branches | application development and the pinned validator commit |
| `catalogue` | marketplace data: `publishers/`, `packages/`, generated `artifacts/` and `index.json`, `moderation.json`, its own Validate and Publish workflows |

The files come from two folders in this source tree:
- **[`marketplace/catalogue-repository/`](../../marketplace/catalogue-repository/)**
  becomes the root of `catalogue`. Its
  [MAINTAINERS.md](../../marketplace/catalogue-repository/MAINTAINERS.md)
  covers setup, rules, review and releases;
  [CONTRIBUTING.md](../../marketplace/catalogue-repository/CONTRIBUTING.md)
  covers publishing.
- **[`marketplace/default-branch/`](../../marketplace/default-branch/)**
  holds exactly two files, installed on `main`:
  `.github/workflows/submission-paths.yml` and the `.github/CODEOWNERS`
  lines that protect it.

Patchwork users set the marketplace source to `<owner>/<repo>` with branch
**`catalogue`**. An empty branch means `main`, where there is no
`index.json`.

No production repository is built into Patchwork or the templates. The
workflows take the repository identity from GitHub (`GITHUB_REPOSITORY`),
and the validator source from the repository variables
`PATCHWORK_REPOSITORY` and `PATCHWORK_COMMIT`. The validator is built from
that pinned commit, never from a submission or from `main`.

## Why the guard lives on `main`

Since 8 December 2025 GitHub always takes `pull_request_target` workflows
from the repository's default branch, never from the pull request's base or
head. So the guard is installed on `main`, filtered to pull requests that
target `catalogue`, and a pull request can never change it for its own run.
`validate.yml` and `publish.yml` stay on `catalogue`:
- `pull_request` workflows come from the merge result;
- push workflows come from the pushed commit;
- GitHub offers manual runs only for default-branch workflows, so Publish
  has none. Re-run the latest Publish run instead.

The application's workflows never run for the catalogue, because
`catalogue` does not contain them.

## The validator is Patchwork

CI runs the Patchwork binary in its headless mode:

```text
patchwork catalogue validate          --root DIR --repository OWNER/REPO [--branch B]
patchwork catalogue check-pr          --base DIR --head DIR --repository OWNER/REPO [--branch B]
                                      --author-login LOGIN --author-id ID [--maintainer]
patchwork catalogue publish-artifacts --root DIR --repository OWNER/REPO [--branch B]
patchwork catalogue publish-index     --root DIR --repository OWNER/REPO [--branch B]
                                      --commit SHA --generated-at UNIX_SECONDS
patchwork catalogue check-paths       --repository OWNER/REPO --pull-before FILE
                                      --pull-after FILE --pages DIR --head-sha SHA
                                      --default-branch B --maintainer-ids "ID,ID"
```

`check-paths --default-branch` is the branch submissions must target. The
guard passes `catalogue`, not GitHub's default branch. The single-repository
layout needed no validator change: the pinned commit
(`1cc2045f9b334047afada25f19b67b62d9c9bd45`, tag
`catalogue-validator-p4.3.4`) supports it as is.

The mode is selected by the first argument and exits before any window,
setting or device is touched (`src/main.rs`). The code is
`src/library/marketplace/repository.rs`, with the command line in
`repository/cli.rs` and tests in `repository/tests.rs`.

There is one implementation of every rule. The desktop app and CI share:
- the artifact format and order (`submit::build_artifact`);
- SHA-256 over the whole artifact;
- the catalogue validator (`parse_catalogue`);
- the installer's artifact checks (`verify_download`, `parse_artifact`);
- the capability scan with its restricted node types;
- the secret scan;
- the history check (`check_refresh`).

So an artifact generated by CI is byte-identical to the one Share to
Marketplace reported, and a catalogue CI accepts is one Patchwork accepts.

## Layout additions

These go beyond architecture §3:
- **`min_app_version`.** Each version's `package.json` must state
  `min_app_version`; the catalogue's `min_patchwork` is taken from it. Share
  to Marketplace writes it.
- **Capabilities** listed in the catalogue are the scanned ones. The scan is
  authoritative, so declared equals detected.
- **`moderation.json`** (maintainer-only) holds withdrawn versions:
  `{"yanked": {"<id>@<version>": "<reason>"}}`.
- **`.gitattributes`** is `* -text`: published files are hashed byte for
  byte, so no line-ending conversion is allowed. The workflows also set
  `core.autocrlf false`.

## What a pull request may change

Submissions are pull requests with base `catalogue`.

| Change | Allowed for |
|---|---|
| add `publishers/<ns>.json` | the PR author's own account only: login and **numeric id** from the pull request event |
| add `packages/<ns>/<name>/<version>/…` (new version) | the namespace's owner (numeric id) |
| add or update `package.meta.json`, package `README.md` | the namespace's owner |
| change an existing claim, `moderation.json`, `catalogue`'s `.github/`, docs | maintainers (`MAINTAINER_IDS`) |
| remove a version folder (takedown) | maintainers |
| change files in a published version folder | nobody |
| edit `artifacts/`, `index.json` | nobody (generated) |

After the path rules, the whole merge result is validated against the
published `index.json`. This covers:
- every rule of the catalogue schema: reserved and look-alike namespaces
  and names, one namespace per account, ids, canonical versions and text
  limits;
- each version as an artifact: safe paths, file limits, UTF-8, manifest,
  checksums, `source: "marketplace"`, bundled dependencies, secrets and node
  types;
- bundled dependencies that are exact copies of published versions in the
  catalogue;
- preview images (allowed name, at most 2 MiB, real PNG/JPEG/WebP bytes);
- unchanged published history.

A version that was taken down can only return with exactly its published
bytes, because its artifact file stays.

## Publication

On `catalogue` after merge (`publish.yml`, on pushes to `catalogue` only):
1. validate;
2. `publish-artifacts`: write the artifacts of new versions; any existing
   artifact must rebuild to exactly its bytes;
3. commit;
4. `publish-index --commit <that commit> --generated-at <its time>`:
   - new versions (and their previews) are pinned to that commit, which
     contains them;
   - published versions keep their pins;
   - `generated_at` never decreases;
   - the result must pass `parse_catalogue` and `check_refresh` against the
     previous index;
5. commit and push to `catalogue` with the deploy key.

Pushes made with the deploy key start the workflow again. That run finds
nothing new, because both commands are idempotent. Download URLs are
`https://raw.githubusercontent.com/<owner>/<repo>/<commit>/artifacts/…`,
pinned to a commit on `catalogue`, so they never change.

## Trust boundaries

- Pull-request workflows use `pull_request` (read-only token, no
  secrets), check out the validator from the pinned Patchwork commit, and
  pass PR values through environment variables only.
- A contributor PR can rewrite `catalogue`'s `validate.yml` for its own
  run, so on its own a green "Validate submission" proves nothing. The
  required **Submission paths** status closes this (`submission-paths.yml`
  on `main`, `repository/paths.rs`):
  - It runs on `pull_request_target` from `main`, only for pull requests
    targeting `catalogue`.
  - Job `check` can only read (`contents`, `pull-requests`). It checks out
    and builds only the pinned validator, and nothing from the PR.
  - It reads every page of GitHub's changed-file list and the PR record
    before and after. It fails closed if the list is incomplete or
    inconsistent, if the API returns an error, if there are more than 3000
    files, if the head changes during the check, or if the PR does not
    target `catalogue`.
  - It refuses any change outside `publishers/` and `packages/`, checking
    renames at both ends, unless the author's numeric id is in
    `MAINTAINER_IDS`.
  - Nobody may change `index.json` or `artifacts/`.
  - Job `report` (`statuses: write` only; no checkout, no build, no
    secrets) sets the commit status `Submission paths` on
    `github.event.pull_request.head.sha` from `check`'s result.

  When both pass, the PR has not touched `.github/`, so "Validate
  submission" ran the reviewed workflow.
- Publication re-validates everything, and changes under `.github/` also
  need CODEOWNERS review: `catalogue`'s CODEOWNERS for the catalogue
  workflows, `main`'s for the guard.
- Namespace ownership comes from GitHub's pull request event (numeric
  account id), never from typed names. Namespace owners and maintainers
  approve through CODEOWNERS.
- Nothing in the catalogue is executed by CI or by Patchwork's installer.
  Packages run only after the user allows them, with their approved
  capabilities (P4.3.2).

### Why a commit status, and what `statuses: write` allows

The required check must belong to the PR's head commit and must not be
satisfiable by a contributor. For a workflow sourced from `main`, GitHub
documents neither where its own check run attaches nor how two check runs
with the same name are judged. A **commit status** is set explicitly on the
head commit. GitHub documents that when a check run and a status share a
required name, both must pass. Fork PRs only ever get read-only tokens and
cannot set statuses.

`statuses: write` lets that job's short-lived token create commit statuses
on any commit of the repository, for example a false success on an
application commit. It is confined to job `report`:
- `report` runs no checkout, build, third-party action or repository code;
- it only calls the statuses API with values from GitHub's event and
  `check`'s result;
- the pinned validator and its build dependencies run in job `check`, which
  cannot write anything.

### Deployment gate (live tests)

Rely on the guard only after all of these pass, using a scratch pull
request into `catalogue` from a fork owned by a second account:
1. **Attachment:** the `Submission paths` status appears on the PR's head
   commit (Checks/status list, or `GET /repos/<owner>/<repo>/commits/<head>/status`).
   Choose it as a required check in the `catalogue` ruleset, with source
   GitHub Actions, and confirm a passing PR becomes mergeable.
2. **Failure blocks:** a PR adding `.github/workflows/x.yml` gets a failure
   status and cannot be merged.
3. **Look-alike:** a PR adding a workflow whose job is named
   `Submission paths` and always succeeds still cannot be merged. The real
   status is a failure; both are required.
4. **Stale result:** after a passing run, push a commit touching `.github/`.
   The new head has no success status, so the PR is blocked until the new
   run reports failure.
5. **Fork token:** in a test fork PR, a workflow step calling
   `POST /statuses/<head>` with `GITHUB_TOKEN` is refused (403).
6. **Target:** a PR into `main` does not run the guard. Retargeting a
   passing PR from `catalogue` to `main` and back re-runs it.
7. **Variables:** fork PR runs of Validate see `PATCHWORK_REPOSITORY` and
   `PATCHWORK_COMMIT`. If they do not, Validate fails closed. The fallback is
   to pin the validator repository and commit literally in `catalogue`'s
   `validate.yml`.
8. **Publish:** a merge publishes from `catalogue` only, pins download URLs
   to the artifacts commit, and starts no application workflow. The deploy
   key cannot push to `main` or create tags.
