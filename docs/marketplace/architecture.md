# Patchwork Node Marketplace (P4.3) — Architecture

Status: **P4.3.0, P4.3.1A and P4.3.1B implemented** (catalogue contract; catalogue
browser with cache; verified installation).
Submission tooling, the CI validator and runtime capability grants are not
implemented yet.

Code: `src/library/marketplace.rs` (tests in `src/library/marketplace/tests.rs`).
Example catalogue: [`index.example.json`](index.example.json). A test parses
this file, so it always matches the validator.

---

## 1. Goals and non-goals

**Goals**

- Users can browse a public catalogue of custom nodes and install exact,
  reviewed versions into their existing versioned Library
  (`~/.patchwork/library/packages/<id>/<version>/`).
- No custom backend: the catalogue is a public GitHub repository holding a
  generated `index.json` and immutable artifacts.
- The catalogue is **untrusted input**. A catalogue entry never makes a
  package trusted; Patchwork verifies everything itself.
- Existing behaviour is unchanged: P4.0 flat Library nodes, P4.1 versioned
  packages, P4.2 nested bundles, portable projects, project references and
  read-only package protection.

**Non-goals (for P4.3)**

- Automatic upgrades. Instances keep their exact version; switching is the
  explicit P4.2 Stage 5 "Version →" action.
- Accounts, ratings, payments, or a server.
- Native-code nodes (CLAP or Rust plugins): never distributed through the
  catalogue.
- Executing anything during installation.

## 2. Components

```text
 GitHub repository  (reviewed by maintainers, validated by CI)
 ├── packages/…      unpacked, human-reviewable version folders
 ├── artifacts/…     generated .pwpkg files (immutable once merged)
 └── index.json      generated catalogue
            │
            │ HTTPS GET, raw.githubusercontent.com only (P4.3.1)
            ▼
 Patchwork
 ├── marketplace::parse_catalogue      validate index.json (P4.3.0)
 ├── marketplace::check_refresh        reject rewrites and rollbacks (P4.3.0)
 ├── catalogue cache                   ~/.patchwork/marketplace/ (P4.3.1)
 ├── artifact download + extraction    size/count/path limits (P4.3.1)
 ├── package::verify_version_dir       existing P4.1/P4.2 verification
 ├── capability scan                   declared ⊇ actual (P4.3.1)
 └── Library install                   staging → verify → rename (P4.3.1)
```

The marketplace adds one new way to put a version folder into the Library.
It produces the same folder `publish_package` produces, with the same
manifest format, the same checksums and the same bundle layout. After
installation, the resolver, project bundling, version switching and
read-only protection treat it like any other package version.

## 3. Public repository layout

```text
patchwork-catalogue/                      (repository name and owner to be decided)
├── README.md                             what the catalogue is, how to install
├── CONTRIBUTING.md                       submission guide
├── SECURITY.md                           reporting abuse and takedowns
├── LICENSE
├── .github/
│   ├── CODEOWNERS                        packages/<ns>/** → @<ns owner> + maintainers
│   └── workflows/
│       └── validate.yml                  validation only; never runs package content
├── publishers/
│   └── <namespace>.json                  namespace claim: github login + numeric id
├── packages/
│   └── <namespace>/<name>/
│       ├── package.meta.json             listing metadata (name, description, tags, license, docs)
│       ├── README.md                     optional documentation
│       └── <version>/                    one immutable, reviewable version folder
│           ├── package.json              PackageManifest (source: "marketplace")
│           ├── <Entry>.pwnode
│           ├── deps/<id>/<ver>/…         P4.2 flat bundle, when it has dependencies
│           └── preview.png               optional (png/jpg/jpeg/webp, ≤ 2 MiB)
├── artifacts/
│   └── <id>/<version>/<id>-<version>.pwpkg   generated by CI from packages/…/<version>/
└── index.json                            generated by CI from publishers/ + packages/
```

Repository rules, enforced by CI and branch protection:

1. `index.json` and `artifacts/` are generated. A pull request that edits
   them by hand fails.
2. Existing files under `packages/<ns>/<name>/<version>/` and `artifacts/`
   can never be modified or deleted by a normal pull request. Takedowns are
   maintainer-only commits that remove the entry from `index.json`.
3. Every pull request runs the same validator Patchwork uses
   (`parse_catalogue`, `check_refresh` against `main`,
   `check_artifact_listing`, `check_manifest_matches`), plus
   `verify_version_dir` and the capability scan on each new version. CI
   only parses JSON; it never evaluates graphs or runs scripts.
4. Changes under `packages/<ns>/` need approval from that namespace's owner
   (CODEOWNERS) and a maintainer. The PR author's numeric GitHub id must
   match `publishers/<ns>.json`.
5. Artifacts are built deterministically: rebuilding from the folder must
   give byte-identical files and the same SHA-256.

## 4. Catalogue schema (`index.json`, format 1)

Unknown fields are ignored at every level, so newer catalogues can add
optional data. They never change the meaning of known fields. Duplicate
keys in one JSON object are rejected.

### Top level

| Field | Type | Required | Rules |
|---|---|---|---|
| `kind` | string | yes | exactly `"patchwork-catalogue"` |
| `catalogue_format` | integer | yes | `1`. Higher values mean "update Patchwork"; the cached copy is kept |
| `generated_at` | integer (Unix s) | no | must never decrease across refreshes |
| `publishers` | array | no | ≤ 5 000 |
| `packages` | array | no | ≤ 10 000 |

### Publisher

| Field | Type | Required | Rules |
|---|---|---|---|
| `namespace` | string | yes | the owner's GitHub login in lowercase (see §5) |
| `github` | string | yes | GitHub login |
| `github_id` | integer | yes | numeric account id, non-zero, one namespace per account |
| `display_name` | string | yes | ≤ 100 chars, single line, no control/bidi/invisible chars |
| `url` | string | no | `https://` link (opened in the browser only) |

### Package

| Field | Type | Required | Rules |
|---|---|---|---|
| `id` | string | yes | `<namespace>.<name>`: **the identity**. Namespace must be claimed |
| `name` | string | yes | display only, never identity; ≤ 100 chars, single line |
| `description` | string | no | ≤ 2 000 chars; newlines allowed |
| `author` | string | yes | display only; ≤ 100 chars |
| `tags` | array of string | no | ≤ 12, each `[a-z0-9-]{1,32}`, unique |
| `license` | string | no | SPDX expression, ≤ 64 chars |
| `documentation` | string | no | `https://` link (opened in the browser only, never fetched) |
| `versions` | array | yes | 1–200 entries |

### Version

| Field | Type | Required | Rules |
|---|---|---|---|
| `version` | string | yes | exact canonical `MAJOR.MINOR.PATCH`; no pre-release or build metadata |
| `entry` | string | yes | `<name>.pwnode`: plain ASCII file name, ≤ 100 chars, safe on Windows |
| `manifest_format` | integer | yes | ≥ 1. Not `1` means incompatible (not an error) |
| `pwnode_version` | integer | yes | ≥ 1. Not `1` means incompatible |
| `bundle_format` | integer | no (0) | 0 standalone, 1 complete P4.2 bundle. Higher means incompatible |
| `min_patchwork` | string | yes | canonical version. Newer than the app means incompatible |
| `capabilities` | array of string | no | see §6. Unknown names mean incompatible; `native_code` is an error |
| `artifact` | object | yes | see below |
| `preview` | object | no | see below |
| `published_at` | integer (Unix s) | no | informational |
| `yanked` | string | no | reason. Not offered for new installs; installed copies keep working |

### Artifact

| Field | Type | Required | Rules |
|---|---|---|---|
| `format` | integer | yes | ≥ 1. Not `1` means incompatible |
| `url` | string | yes | `https://raw.githubusercontent.com/<owner>/<repo>/<40-hex commit>/artifacts/<id>/<version>/<id>-<version>.pwpkg`. Must be the catalogue's own repository, pinned to a commit, with no query, fragment, `%`, `..` or credentials |
| `sha256` | string | yes | 64 lowercase hex digits over the **whole artifact file**; not all zeros; unique in the catalogue |
| `size` | integer | yes | exact size in bytes, 1 – 16 MiB |
| `files` | integer | yes | number of files inside, 2 – 256 |

### Preview

| Field | Type | Required | Rules |
|---|---|---|---|
| `url` | string | yes | same repository and pinning rules as the artifact, path `packages/<ns>/<name>/<version>/preview.{png,jpg,jpeg,webp}` |
| `sha256` | string | yes | as above |
| `size` | integer | yes | 1 – 2 MiB |

### Duplicates

- The same `(id, version)` listed twice with identical content is accepted
  once. With different content, the catalogue is rejected.
- The same package listed twice merges its versions if the package metadata
  is identical. Otherwise the catalogue is rejected.
- A namespace claimed twice differently, one GitHub account owning two
  namespaces, or two versions with the same artifact digest are all
  rejected.

### Whole-catalogue rule

Any error rejects the whole catalogue (`CatalogueErrorKind::Invalid`, at
most 100 issues reported), and Patchwork keeps the last good cached copy.
CI runs the same validator, so a rejected catalogue means tampering or a
bug, not a bad package to skip silently. Forward-compatible differences
(newer formats, newer `min_patchwork`, unknown capabilities) are not
errors. They are reported per version through `Compatibility`.

## 5. Identity and ownership

- **Identity is the package id** `<namespace>.<name>` plus an exact
  version. Display names and authors are presentation only. Two packages
  may share a display name, and the UI always shows the id.
- **Namespace = the owner's GitHub login, lowercased.** GitHub logins are
  unique and case-insensitive, so unrelated publishers cannot claim the
  same namespace. `github_id` pins the numeric account: if a login is
  renamed or recycled, `check_refresh` refuses a namespace whose owner id
  changed.
- **Reserved namespaces:** `local`, `builtin`, `core`, `std`, `system`,
  `test(s)`, `example(s)`, `marketplace`, `official`, `patchwork`.
  `patchwork` belongs to the catalogue maintainers: it is valid only when
  its `github` is the catalogue repository's owner. The others cannot be
  claimed.
- **No collision with local packages:** packages published on this machine
  are `local.<slug>`. Public ids can never start with `local.`, so a
  marketplace install can never target a locally published package folder.
- **Look-alike protection:** namespaces, and package names within one
  namespace, that differ only by `-`, `_` or `.` are rejected
  (`acme-io`/`acmeio`, `my-gain`/`my_gain`). Display text rejects control,
  zero-width and bidirectional-override characters.
- **Exact versions only:** instances store `id@version/entry` (P4.2), and
  nothing in the marketplace changes an existing instance's version.

## 6. Trust and security model

**A merged pull request is not a safety guarantee.** Review only filters
spam and obvious abuse. Every protection below holds even if a malicious
version is merged, or if GitHub or the network is compromised.

| Threat | Defence |
|---|---|
| Tampered catalogue or artifact in transit | HTTPS to `raw.githubusercontent.com` only. Artifact SHA-256 and exact size come from the catalogue; per-file SHA-256 comes from `package.json` (`sha256`, `files`) |
| Artifact replaced after publication | URLs pinned to a commit hash. CI forbids modifying published files. `check_refresh` refuses a changed digest, size or entry for a known version |
| Catalogue rollback (serving an old index) | `generated_at` must not decrease (`check_refresh`) |
| Namespace hijack (renamed or recycled login) | `github_id` pinned; an owner change is refused on refresh |
| Path traversal or odd files in artifacts | `validate_artifact_path` accepts only `package.json`, the entry, and `deps/<id>/<ver>/{package.json,*.pwnode}`. It rejects `..`, `.`, absolute and drive paths, backslashes, Windows device names, case-insensitive duplicates and every other file |
| Zip bombs, symlinks, permission bits | The artifact is not an archive. A `.pwpkg` is a single JSON document holding UTF-8 text files, so there is no compression, symlink or mode bit to abuse |
| Oversized or pathological input | Catalogue ≤ 8 MiB, checked before parsing. Artifact ≤ 16 MiB and ≤ declared size (downloads stop at the limit). ≤ 256 files, ≤ 8 MiB per file, ≤ 200 path chars. String, list and URL lengths are bounded. Deep JSON nesting cannot overflow the stack |
| Duplicate-key smuggling | Duplicate JSON keys are rejected |
| Code execution during install | Nothing is executed. Install = download, verify, write files, verify again |
| Privileged nodes | Capability declaration plus an independent scan (below) |
| Unsafe remote-install route | No URL-scheme handler, deep link, MCP command, drag-and-drop URL or project field can trigger an install. Installs only start from an explicit user action in the marketplace UI, and go through the same staging and verification as publishing |

### Artifact format (`.pwpkg`, format 1; implemented in P4.3.1B)

```json
{
  "pwpkg": 1,
  "id": "acme-audio.gain",
  "version": "1.2.0",
  "files": [
    { "path": "package.json", "text": "<UTF-8 text>" },
    { "path": "Gain.pwnode",  "text": "<UTF-8 text>" }
  ]
}
```

Every file a package version may contain (`package.json` and `.pwnode`
files) is UTF-8 JSON, so a JSON envelope needs no archive library and is
diffable. Files are a **list**, not a JSON object, so duplicate paths are
visible instead of being silently merged. Unknown fields anywhere in the
envelope (for example `mode`, `symlink` or `hooks`) are rejected: there are
no permissions, links, timestamps or install hooks. The artifact digest
covers the whole file.

Parsing (`marketplace::artifact`) happens entirely in memory, before
anything is written. It checks:

- the exact size and SHA-256 from the catalogue;
- UTF-8, and JSON nesting of at most 64 levels in the envelope and in
  every file;
- the envelope schema, its format, and that its id and version match the
  catalogue;
- the file count, both against the catalogue and the 256-file cap;
- each file at most 8 MiB, and all files together at most 16 MiB;
- unique paths, compared case-insensitively;
- the package version layout only (`validate_artifact_path`);
- `check_manifest_matches` and the entry checksum;
- that bundled files are **exactly** the set the manifest declares, with
  matching checksums;
- every bundled dependency's manifest, its public id, and that its entry
  exists;
- every declared dependency is bundled at exactly its version, so nothing
  is substituted.

After staging, the existing `verify_version_dir` checks everything again on
the written files.

### Capabilities

Each version declares the privileged capabilities it uses.
`marketplace::scan` classifies **every** `NodeType` variant and **every**
registered dynamic node `type_tag` explicitly. Two unit tests read
`graph.rs` and the live node registry and fail when a node type is
unclassified, or when a table entry no longer exists. The classification is
conservative: a node that *may* touch files, the network, devices, capture
or code counts as using that capability.

| Capability | Examples (see `scan.rs` for the full tables) |
|---|---|
| `filesystem` | FolderBrowser, FileMenu, AudioPlayer, AudioSampler, ImageNode, VideoPlayer, MlModel, AiRequest (writes generated images); `file`, `shape_3d` (glTF path), `tts` (voice config path), `frame_recorder`, ML detection models |
| `network` | OscIn/Out, ArtNetIn/Out, HttpRequest, AiRequest, NetworkSend/Receive, HtmlViewer (loopback server); `websocket` (loopback), `web_stream` and `web_app` (servers reachable from the local network), `text_gen` |
| `devices` | MidiIn/Out, Serial, DmxIn/Out, Ob* hardware nodes, AudioDevice; `key_input`, `midi_note`, `printer` |
| `media_capture` | Camera, AudioInput, audio analysers; `video_in` |
| `scripting` | Script (Rhai), WgslViewer, HtmlViewer; `wgsl_presets`, `code_gen`, `web_app` |
| `process` | VideoPlayer, Camera, AudioInput (ffmpeg); `video_in` (ffmpeg, yt-dlp), `tts` (espeak-ng), `printer` (lp/print), `monitor`, `web_stream`, `web_app`, `video_out` |
| `system_info` | `monitor` (hardware, load and process information) |
| `ai_credentials` | AiRequest, `text_gen`, `image_gen`, `code_gen` (use the AI keys and endpoints stored in Patchwork) |
| **refused** | ClapPlugin, RustPlugin (native code); McpServer (external control of Patchwork); `terminal` (system commands); `settings` (Patchwork settings); `ai_config` (stored AI credentials) |

`process`, `system_info` and `ai_credentials` were added in P4.3.2B.
Patchwork versions without them treat them as unknown capabilities, so such
packages are reported as incompatible there, never silently allowed.

**Classification version.** `scan::CLASSIFICATION_VERSION` (currently 2)
changes whenever a node type is reclassified. Each installation reports the
version it was checked against, so future trust records can be reconsidered
when it changes.

**Source audit guard.** The classification was checked against the node
sources (constructor, state loading, evaluation, rendering, threads, files,
network, devices, capture, processes, scripting). A unit test keeps it
honest. It reads every node source file and maps privileged APIs to
capabilities: `std::fs`, sockets and HTTP, serial/MIDI/HID, input streams,
`Command::new`, Rhai, `sysinfo` and the AI key store. It fails when a node
uses one that its classification does not include. Exceptions are listed
with reasons: file dialogs and "Open in editor" buttons that only the user
can trigger, a fixed preset folder, and the expression-only Math formula
engine.

**Scripts.** Every Rhai engine that runs graph code (Script and Math
formula nodes) comes from `scripting::sandboxed_engine`. It has no module
imports, no `eval`, finite operations and wall-clock time per run, bounded
expression depth, call depth, string, array and map sizes, `print`/`debug`
going to the system log, a source-size limit, and plain identifiers for
injected variables. A runaway script becomes a node error instead of a
hang. The remaining risk is CPU use up to the per-run limit on every frame,
and memory within the size limits.

**External programs.** No program is started through a shell; files and
URLs are opened with the OS handler. ffmpeg inputs carry an explicit
`-protocol_whitelist`: network protocols for URLs, `file` for paths, and
other schemes (`file:`, `concat:`, `subfile:`, `data:`, `pipe:`) are refused.
`yt-dlp` gets the URL after `--` and only accepts `http(s)` URLs.
`espeak-ng` gets its text after `--` and a validated voice. `lp` gets `--`
before the document; printer names and document paths can't start with `-`.
The recorder's output path can't start with `-`.

**Secrets.** Publishing to the Library and installing from the marketplace
refuse graphs containing obvious credentials. These are credential-named
fields with a value (for example a key stored in an AI Request node),
`Authorization`/API-key headers, and well-known key formats. Messages name
the location, never the value. Existing projects are never modified.

How these are identified and handled:

1. **Detection is independent of the declaration.** Patchwork scans the
   raw JSON of every `.pwnode` in the artifact, including bundled
   dependencies, *before* anything is deserialized. This matters because a
   normal load silently replaces an unknown dynamic node with an `AddNode`.
   Unknown variants, unknown or missing `type_tag`s, unreadable node types
   and refused types block the install. The scan fails closed.
2. **Declared must cover detected.** If the artifact uses a capability it
   does not declare, the install is refused. Declaring more than is used is
   allowed; the consent dialog shows the declaration.
3. **Consent.** Every install needs an explicit confirmation in a dialog
   showing the package, version, publisher, declared capabilities, and that
   **installation does not sandbox nodes**. Browsing and refreshing never
   install anything.
4. **Runtime gate (P4.3.2D).** A package runs only when the trust store
   authorizes its exact content (see "Runtime permissions" below).
   Installation consent never grants execution.
   Packaged instances from marketplace packages whose capabilities were not
   granted on this machine, for example from a project received from
   someone else, load but stay inactive until the user grants them.
5. Unknown capability names from newer catalogues make the version
   incompatible. They are never ignored.

### Provenance and the trust store (P4.3.2C)

`~/.patchwork/trust/packages.json` lives outside the Library, so nothing
inside a package, a project or the Library can write it. It records where
Patchwork itself saw each exact package version come from. Nothing is
enforced from it yet: runtime grants and prompts come in a later stage.

**Content identity.** A record applies to `id`, `version` and the SHA-256
*tree digest* of the complete version folder (`package.json`, the entry
and every bundled dependency), all three matched exactly:

```text
SHA-256( "patchwork-package-tree\0"  u32be(1)  u64be(file count)
         for each file, sorted by the bytes of its path:
           u64be(path length) path  u64be(size) SHA-256(file) )
```

Paths are canonical: relative, `/`-separated, plain ASCII segments. Anything
that systems could read differently is refused: `.`/`..`/empty segments,
`\`, `:`, `*?"<>|`, control characters, leading spaces, trailing dots or
spaces, Windows device names, non-ASCII names (Unicode normalization
differs between file systems), case-only collisions, links and special
files. Empty folders are not content. A unit test pins the digest of a
fixed tree to a value computed independently, so the construction cannot
drift between platforms or versions.

**Schema (format 1).**

```json
{
  "schema": "patchwork.trust.packages",
  "format": 1,
  "legacy_review": "pending",
  "records": [{
    "id": "acme-audio.gain", "version": "1.2.0",
    "tree_format": 1, "tree_sha256": "<64 lowercase hex>",
    "provenance": {
      "kind": "marketplace",
      "owner": "patchwork-nodes", "repo": "catalogue", "branch": "main",
      "catalogue_generated_at": 1700000000,
      "catalogue_sha256": "<SHA-256 of the validated catalogue text>",
      "artifact_url": "https://raw.githubusercontent.com/…/acme-audio.gain-1.2.0.pwpkg",
      "artifact_sha256": "<catalogue artifact digest>"
    },
    "classification_version": 2,
    "declared_capabilities": ["network"],
    "detected_capabilities": [],
    "restricted_node_types": [],
    "unclassified_node_types": [],
    "grant": "not_granted",
    "recorded_at": 1700000100
  }]
}
```

* `provenance.kind` is `local_publish` (no other fields), `marketplace`
  (above) or `imported` with `"origin": "legacy_library"`.
* `declared_capabilities` is present for marketplace records only (`null`
  otherwise); detected must be a subset of it. Local records also list node
  types the marketplace forbids or does not classify.
* `grant` is `not_granted`, `granted` or `denied`. Publishing, installing
  and accepting in the review all record `not_granted`; denying records
  `denied`.
* `legacy_review` is `pending`, `declined` or `completed`.

**Writing.** Only trusted workflows can add a record: the store accepts a
`ProvenanceReceipt`, which only `crate::library` code can create, and only
for a folder whose digest equals the digest of the content that workflow
verified:

* *Publish to Library*: the staged folder's digest must equal the committed
  folder's digest.
* *Marketplace install*: the digest of the verified artifact files (in
  memory) must equal the committed folder's digest, or the install is
  rolled back. The record names the catalogue source, its `generated_at`
  revision, the SHA-256 of the validated catalogue text and the artifact's
  URL and digest. The consent dialog can only be opened for the verified
  catalogue currently shown for the configured source.
* *Package Trust Review*: the user's decision for the reviewed digest.

A record is written only after the operation succeeded. Failed, refused,
interrupted and cancelled operations write nothing. A failure to record
never undoes a successful publish or install: the version simply has no
record, and is listed for review. The manifest `source` field, `local.*`
ids and the location of a folder (Library or project) are never used as
provenance.

**Files.** Writes are read-modify-write under a process lock: a temporary
file in the same folder, flushed, then renamed over the store. The file is
`0600` and the folder `0700` on Unix; on Windows it inherits the user
profile's permissions. Reading is strict: unknown fields, unknown
capabilities, grants or provenance kinds, malformed ids, versions or
digests, a newer format or classification, a `id@version` listed twice,
oversized or non-regular files all make the store *damaged*. A damaged
store records nothing (every package is "no record"), is never written
over, and can only be moved aside by the user (`packages.damaged-<time>.json`)
from the review window.

**Statuses.** For a package folder anywhere (Library or a project's
`packages/`): *no record*; *content changed* (a record exists for the
`id@version` but another digest, so it does not apply); *reclassified* (the
record's classification version is older; the user re-checks it, which
keeps the provenance and turns a grant back into `not_granted`); or
*recorded*. A project copy is recorded only if it is byte-for-byte the
recorded content; placing a package inside a project grants nothing.

**Migration.** Packages that were in the Library before the trust store
have no record. At start-up, if the review is pending (or the store is
damaged) and such packages exist, the *Package Trust Review* window
(Library menu) lists them with the manifest's claimed source (shown as a
claim), detected capabilities and restricted or unknown node types. For
each, the user can *Accept* (recorded as `imported`, origin not verified,
`not_granted`) or *Deny*. *Later* defers to the next start; *Don't migrate*
stops the automatic prompt; *Done* completes it. `local.*` packages are
never marked as locally published, package bytes are never changed, and
projects keep working whatever is decided.

### Runtime permissions (P4.3.2D)

**One gate.** Every package runtime is built in `Graph::load_custom_runtime`:
a top-level or nested instance, from the palette, a project or its
`packages/`, session restore, paste, duplicate, undo/redo, version
switching, MCP `UpdateNode`/`LoadProject`, or a refresh. Before anything is
constructed, `trust::authorize::authorize_entry`:

1. verifies the version folder statically;
2. hashes it again (tree digest) and reads the manifest from those bytes;
3. looks up the record for exactly `id`, `version` and digest;
4. checks the record's classification version;
5. rescans the hashed graphs' capabilities;
6. checks the grant (or the local-author policy);
7. does the same for every package the entry depends on, resolved exactly
   as the runtime will resolve them (bundled `deps/` first).

The runtime is then built from the very text that was hashed, not re-read
from disk. The recursion check and the version-switch planner read files
statically, and palette insertion reads only the interface, so nothing in a
package is constructed before it is authorized. A package version opened in
a tab (Library, project copy or bundled dependency) goes through the same
check, because the tab's graph is evaluated. MCP `CreateNode` cannot create
custom-node instances.

**Decisions.**

| Record | Result |
|---|---|
| none | needs permission |
| another digest for the same `id@version` | blocked (conflict; cannot be granted over) |
| older classification | needs a new decision |
| `denied` | blocked; not offered again automatically |
| `granted`, rescanned capabilities within the approved set | runs |
| `not_granted`, provenance `local_publish` | runs (local-author policy) |
| `not_granted`, any other provenance | needs permission |
| damaged store / no store configured | blocked |

*Local-author policy.* Only a `local_publish` record (written by Patchwork's
Publish workflow for exactly these bytes) runs without a prompt. Marketplace
installs, migration-accepted and project-bundled packages, and unrecorded
packages always need an explicit grant, even with no privileged
capabilities. An id prefix, manifest field or folder location never counts.

*Grants.* `TrustStore::grant` identifies the folder again and requires the
reviewed identity (same bytes), rescans it, records `granted` with
`approved_capabilities` (the rescanned set) under the current
classification, and never replaces a record for another digest of the same
`id@version`. A package without a record is recorded as `imported` with
origin `execution_review`. `TrustStore::deny` records `denied`; only an
explicit grant reverses it. `approved_capabilities` is optional in the file
(P4.3.2C stores stay readable) but must be present, and cover every detected
capability, on a `granted` record.

*Dependencies.* Each dependency needs its own authorization; a granted
parent never authorizes another package. A bundled dependency is identified
by its own folder (`deps/<id>/<version>/`); when its bytes equal the Library
version's, that content's record applies. While any dependency is blocked
the parent's runtime is not built.

**Blocked nodes.** The instance, its ports, connections and reference are
kept; nothing inside runs and no substitute node is used. The node is
labelled "Needs permission" (or "Blocked") and its error tooltip says why.

**Revocation and caching.** Every change to the store made by this process
bumps a trust generation. Running runtimes remember the identity and
generation they were authorized under. On a new generation they are
authorized again from the bytes, and kept only for the same identity. This
also applies to runtimes carried in cloned graphs and undo snapshots. A
blocked state is re-checked when the generation changes (so a grant takes
effect on the next frame) and otherwise every 5 seconds. Blocked results are
cached per folder metadata fingerprint, store file stamp and generation, so a
blocked package is not hashed every frame. An authorization is never cached:
it is recomputed from the bytes right before a runtime is built.

**User experience.** No popups at start-up: a single banner, "N packages need
permission to run — Review", opens **Library → Package Permissions**. It lists
each package once, with its name, `id@version`, verified origin or "Origin
not verified", digest, declared and detected capabilities, and restricted or
unclassified node types. It warns that running is not sandboxed. *Allow to
run* requires ticking an acknowledgement. *Deny* is available too. The editor
keeps running while packages are unresolved.

### Projects and loose custom nodes (P4.3.2E1)

Packages have immutable identities. Projects and loose `.pwnode` files
change all the time, so their trust follows the **content Patchwork wrote**.

**Identity.** A SHA-256 over the canonical JSON (sorted keys, compact) of
the content: a project's or session's `graph`, or a whole `.pwnode`, with a
kind tag. The following are not part of it, and none of them is ever
evidence of provenance:
- file names and folders;
- `project.json` view fields (zoom, offset, pinned nodes);
- keys and recent projects in the session file;
- any field claiming where the file came from.

A byte-identical copy is the same content. Any change to the graph is
different content.

**Content ledger** `~/.patchwork/trust/content.json` (next to the package
trust store):

```json
{ "schema": "patchwork.trust.content", "format": 1,
  "entries": [ { "kind": "project", "sha256": "<64 hex>",
                 "decision": "authored", "recorded_at": 1700000000 } ] }
```

| Decision | Meaning |
|---|---|
| `authored` | written by Patchwork from content that was itself authored on this computer |
| `allowed` | the user allowed it, or Patchwork wrote it from content the user had allowed |
| `denied` | the user refused it; automatic records never replace a denial |

It is parsed strictly, written atomically (`0600` on Unix) and capped at
20,000 entries. The oldest `authored`/`allowed` entries are dropped first;
their content simply needs a decision again. A damaged ledger counts nothing
as authored and is not overwritten.

**What each case becomes:**

| Content | State |
|---|---|
| a new project or custom node created in the editor | authored |
| a project, session or custom node saved here from authored content | authored |
| a saved copy of allowed content | allowed |
| a project or file brought from another computer, edited outside Patchwork, or saved by a Patchwork before P4.3.2E1 | origin not verified (these cannot be told apart) |
| imported content, saved again by Patchwork (Save, Save As, session) | still not verified: nothing is recorded |
| content the user allowed / denied | allowed / denied |

**Where it is enforced.**
- *Top-level graph.* Every graph read from a file starts as not verified (a
  deserialized `Graph` defaults to it; only `Graph::new()` is authored).
  Loaders tag it with its content digest; the editor looks that up in the
  ledger. This covers File → Open and recent projects, session restore
  (session graph or reopen-from-disk), MCP `LoadProject`, and custom-node
  tabs. A graph that may not run keeps its nodes, wires, settings and
  editability. For the runtime part of each frame (device polling,
  evaluation, hardware, native plugins, image and audio processing) and for
  the audio engine, the editor substitutes an empty graph, so nothing in it
  runs and every subsystem closes what it had opened. Node bodies are drawn
  as inert placeholders (editor chrome excepted) with standard ports, so
  wiring still works. Unknown dynamic node types stay inert placeholders
  that keep their serialized state (P4.3.2A).
- *Loose custom-node runtimes.* An instance of a `.pwnode` outside any
  package is authorized like a package, by its content, in the same
  runtime gate, and built from the exact text that was checked.
- *Independence.* Allowing a project never allows a package or a loose
  custom node it uses, and allowing those never allows the project.
- *Saving and copying.* Project Save and Save As, custom-node Save and Save
  As, the session, Group into Custom Node and Duplicate for Editing record
  the digest of exactly what they wrote, with the decision of the content
  they came from, and nothing for content that may not run. Undo and redo
  keep the document's current decision. Pasting a node copied from a
  document that may not run into one that runs is refused. Node duplicate
  stays within one document.
- *MCP.* `LoadProject` is identified like any project. `CreateNode`,
  `UpdateNode` and other edits act on whatever document is open and run
  only if it may run; MCP is treated as local automation configured by the
  user.
- *Player.* There is no standalone Player in this crate. Any future player
  must apply the same top-level and runtime gates.

**User experience.** One banner covers everything waiting for a decision,
for example "This project is not running: its origin is not verified · 2
items need permission". **Library → Permissions** shows the document's
state and digest, and lists every blocked package and custom-node file it
uses. Each one needs its own acknowledgement and *Allow to run* or *Deny*.

**Limits.**
- The ledger is a local record, not a signature. Software running as the
  user can edit it, and "authored" only means that this computer's Patchwork
  wrote that content from content it considered authored. It does not mean
  the content is safe.
- Projects from before P4.3.2E1 and from other computers cannot be told
  apart. Each needs one decision. Hand-edited `project.json` or `.pwnode`
  files need one again.
- Pruning can make very old content need a decision again.
- MCP edits to an open, runnable document run.
- Assets (media, models, scripts embedded in nodes) are part of the graph
  only as stored values. Media files referenced by path are not identified.

### Capability enforcement (P4.3.2E2)

P4.3.2D and P4.3.2E1 decide *whether* a graph runs. P4.3.2E2 decides *what*
a running graph may do. It does this at the privileged operation itself,
not only by classifying node types.

**Rights of a running graph.** Each graph that runs has a capability
context (`src/capability.rs`): a set of capabilities plus a revocation
flag.

| Graph | Its own rights |
|---|---|
| the open document, authored here | every capability (local-author policy) |
| the open document, allowed by the user | exactly the capabilities approved (stored in the content ledger, format 2) |
| a document that may not run | none (and it does not run, P4.3.2E1) |
| a package runtime with a grant | its approved capabilities, plus those of the restricted node types its grant covered |
| a package runtime under the local-author policy | every capability |
| a loose custom node | every capability when authored, else its approved capabilities |

A nested runtime gets its own rights **intersected** with the rights of
the graph that contains it, at every level:
- a child never has more than its parent;
- a trusted parent never lends a child more than the child was approved for;
- a runtime without a record gets nothing.

**Where a context is in force.**
- The editor enters the open document's context for the whole frame:
  - node evaluation;
  - node drawing (where node UIs act);
  - device managers;
  - the audio engine;
  - MCP processing.
- A runtime enters its own context while it evaluates.
- Worker threads started with `capability::spawn` keep the context of the
  code that started them. Every server, reader, decoder and download
  worker that performs privileged work does this.
- Node construction (loading, cloning, pasting, undo) runs with **no**
  rights. Initialization can never act on another document's rights; this
  matters because projects are loaded mid-frame.
- A thread without a context is denied everything (**fail closed**).

**Revocation.** A context is revoked when:
- its document closes, or another project is loaded in its place (the
  document's context belongs to the open document, so undo, redo and the
  frame gate do not revoke it);
- its custom-node runtime is removed (its grant or file decision was
  withdrawn);
- its grant narrows (a new approval, or a re-authorization with a smaller
  set).

A revoked context denies everything. Workers check before every operation;
listeners and readers also check in their loops, then stop and release
their socket, port or pipe. Managers stop delivering data and close what
they opened on behalf of a node that lost the right.

**Approval.**
- Allowing a document approves exactly the capabilities its nodes use,
  which are shown before the decision.
- Saved copies inherit the approved set.
- A running document that uses more than it was approved for shows
  "uses … without your approval". Its nodes are refused those operations
  until the user approves them in **Library → Permissions** (with an
  explicit acknowledgement). The window also lists recently refused
  operations.
- Ledger entries written by P4.3.2E1 (format 1) carry no set. Such content
  keeps running but has no privileged capability until approved again.

**Edits and MCP.**
- Edits never widen an allowed document's rights. A node the user adds to
  an imported document stays limited to the approved set, including after
  Save, Save As and restart.
- An MCP edit that brings in a capability the document's nodes did not use
  before is **withheld**: the document becomes allowed with its previous
  rights minus that capability. This applies to authored documents too, so
  MCP can never turn unapproved executable content into authored content.
- MCP edits that use a capability the document already used are not
  distinguished. Grants are per capability, not per target.

**Enforcement points.** Every check sits at the operation boundary, so it
also covers shared helpers and every node using them.

| Capability | Boundaries |
|---|---|
| filesystem | File, Folder and Folder Browser nodes (reads, listings); Text Editor, Theme, Script and Rust Plugin load/save; audio file playback, decode (every open, including loops) and duration probes; image load and save; glTF meshes; ML and neural-audio models and labels; TTS voices; sampler WAV export; file recorder; AI image results; Settings node |
| network | OSC, Art-Net and Network Send/Receive (send, listen, deliver); HTTP requests (queue and worker); image downloads; ffmpeg URL sources; yt-dlp; NDI find/send/receive; WebRTC offers and frames; HTML, Web App, Web Stream and WebSocket servers (bind, accept, client loops); LAN address detection |
| devices | MIDI connect/send/receive; serial connect/send/read; DMX open/send/listen; OB hubs (connect, poll, commands, device values); HID device values; key and mouse input reaching the graph; printers; Video Out window, Syphon, Spout and virtual camera; the output device chosen by an Audio Device node (without the capability, the default output is used) |
| media capture | microphone streams; camera, screen and dshow/alsa audio capture through ffmpeg |
| process | every ffmpeg/ffprobe decoder and encoder; yt-dlp; espeak-ng; print commands; Terminal; "Open in editor" and "Open in browser"; system tools for the GPU name; Rust Plugin builds |
| system information | System Monitor sampler and hardware queries |
| AI credentials | the AI configuration store (`~/.patchwork/ai_configs`, read, list, write, delete) and stored or environment API keys |
| scripting | Script node execution; WGSL shader compilation and rendering; servers serving page code (HTML viewer, Web App) |
| native code | CLAP plugin loading; Rust plugin build and load |

**External resources.** Approval covers graph content. Resources a graph
refers to by path are data. Reading them needs the capability the read
needs, and whatever runs from them runs with the graph's rights:
- a changed media, model, shader or script file never gains a capability
  the graph lacks (a file-fed script still needs scripting);
- the files and model formats involved cannot load native code.

Native code is different, because it can do anything once loaded:
- **CLAP binaries** are pinned by SHA-256 per path on first load
  (`~/.patchwork/trusted_plugins.json`, `native_pins`). A different binary
  at that path is refused until the user approves it again on the node.
- **Rust plugin libraries** are identified when the node builds them and
  verified before every load.

**Not gated: the editor's own operations.**
- Opening and saving documents, the Library and Marketplace.
- Firmware flashing (`hardware.rs`, run by the user from a menu).
- Device and display enumeration with fixed helpers (camera, MIDI, serial
  and audio device lists).
- The HID enumeration thread.
- Audio output on the default device.
- The MCP stdio service.
- The editor's own caches and preset folders (image cache, WGSL user
  presets).

None of these is driven by graph content.

**Limits.**
- Checks are cooperative calls at the boundaries found by the audit, not
  an operating-system sandbox. A new privileged call site must add its own
  check; review is the safeguard.
- Native code, once loaded, can do anything.
- Capabilities are coarse: a grant of "network" covers any host, and
  "filesystem" any path.
- Revocation stops further operations. It does not undo completed ones,
  and it cannot interrupt a blocking call already in progress (an HTTP
  request, a running program).
- Some resources are released only at the worker's next check. A
  listening socket closes when the next connection arrives, and an ffmpeg
  process started before revocation is left without a reader until its
  node stops it.
- The Math Formula node evaluates bounded expressions without host
  functions and is not treated as scripting.
- The node classification (`scan.rs`) is still used to compute what a
  graph uses for approval. A node type that performs an operation its
  classification does not list is still refused at the boundary unless
  the context allows it.

### Permission management, revocation and recovery (P4.3.2F)

**Open documents follow their decision.** Every open document's decision
is bound to an exact identity:
- a project or loose custom node: the content digest it was opened, last
  saved or decided as;
- a published package version open in a tab: its entry, authorized as a
  package.

When any grant or decision changes (a new trust generation), every open
document is checked against its identity at once, whether it is shown or
in a background tab:

| Change | Effect on the open document |
|---|---|
| denied | stops; its context is revoked, so its workers stop too |
| revoked (no decision any more) | allowed content stops and needs a decision again; content authored in this session keeps running |
| approval narrowed | loses exactly what was withdrawn |
| approval widened, or allowed again | gains exactly what was explicitly added |
| package grant revoked | a package tab stops |

In every case the document's nodes, wires and editability are kept.
Undo and redo never change a document's decision. A lineage record (saving
allowed content elsewhere) never re-allows denied content: only an
explicit decision does.

**Library → Permissions → Recorded permissions** lists:
- **projects and custom-node files** (by content digest, with the
  approved capabilities): revoke an approval, change it, or allow denied
  content again;
- **packages** (by `id@version` and tree digest): revoke, deny, narrow, or
  lift a denial (which only offers the package for review again);
- **native plugins**: CLAP binary pins and approved Rust plugin sources;
  either approval can be withdrawn;
- **recently refused operations**.

Any approval beyond what was approved before needs an explicit
acknowledgement. Package grants are never widened here (widening goes
through the review, which rescans the content).

Withdrawing a native approval takes effect without a restart:
- a loaded CLAP plugin is unloaded;
- a built Rust plugin library is no longer loaded.

A withdrawn CLAP binary is refused until approved again; it is never
re-pinned on first use.

**Recovery.** Damaged records are never trusted, never written over, and
never treated as empty.

| Damaged or interrupted | Recovery |
|---|---|
| trust store | moved aside (kept for inspection); a new, empty store is used |
| content ledger | moved aside; open allowed content stops; nothing it covered is trusted again by itself |
| plugin approvals | moved aside; afterwards every CLAP binary needs an explicit approval (no first-use pinning) |
| interrupted install or publish | staging folders (`packages/<id>/.staging-*`, never scanned or loaded) can be removed. Only real folders with that name directly inside the Library's `packages/<id>/` are removed. |
| granted marketplace package, version later withdrawn or no longer listed | flagged in the window, with a one-click revoke; the grant is not changed by itself |

## 7. Compatibility with existing packages

| Existing behaviour | How P4.3 keeps it |
|---|---|
| P4.0 flat Library nodes (`library/nodes/*.pwnode`) | Untouched; the marketplace only writes under `packages/` |
| P4.1 versioned packages | Same folder layout and `PackageManifest`. Marketplace manifests set `source: "marketplace"` (already reserved) |
| P4.2 bundles | `bundle_format` is carried in the catalogue. Dependencies require a complete bundle of public ids (`check_manifest_matches`), so nothing resolves against the user's own Library |
| Portable projects | Installed versions are ordinary package versions; saving a project copies them into `project/packages/` as today |
| Project references | Unchanged (`id@version/entry`). A project using a marketplace package opens offline from its bundled copy |
| Read-only protection | Installed folders are package versions, so `is_inside_published_package` keeps them read-only. Editing uses Duplicate for Editing (which creates a `local.*` package) |
| Never overwrite | Installing into an existing `packages/<id>/<version>/` is refused unless its content is identical (same manifest and checksums), which counts as already installed. Public ids never use `local.`, so local packages cannot be targeted |

Catalogue metadata (`CatalogueVersion`) and the installed manifest
(`PackageManifest`) stay separate types. `check_manifest_matches` requires
that the artifact's `package.json` has the same id, version, entry and
formats, `source: "marketplace"`, and a `min_app_version` no newer than the
catalogue's `min_patchwork`.

## 8. Offline behaviour

- **Cache** (implemented in P4.3.1A): one file,
  `~/.patchwork/marketplace/catalogue-cache.json`. It holds the last
  *valid* catalogue text verbatim, its SHA-256, the source
  (owner/repo/branch), the fetch and last-check times, and the HTTP ETag.
  It is written atomically (temporary file, `fsync`, rename) and validated
  again on every load. A damaged cache, or one for another source, is never
  shown.
- **Refresh** is explicit (the Refresh button). It runs on a worker thread
  with a 10 s connect and 30 s total timeout, so it never blocks the UI or
  startup. Opening the window only reads the cache. Data last confirmed
  more than 7 days ago is labelled "may be out of date".
- **Source:** there is no built-in production source. The repository is
  configured explicitly (Settings → `marketplace.owner/repo/branch`, or in
  the Marketplace window) and validated before use.
- **Refresh outcomes**

  | Outcome | Behaviour |
  |---|---|
  | Success | Validated, passes `check_refresh` against the cache, replaces the cache |
  | Network error, timeout, HTTP error | Keep the cache; show "Offline — catalogue from <date>" |
  | Invalid catalogue, rewrite or rollback | Keep the cache; show a warning; log the issues |
  | `UnsupportedFormat` | Keep the cache; prompt to update Patchwork |
  | No cache and no network | Marketplace shows "unavailable"; the rest of Patchwork is unaffected |

- **Installed packages never depend on the catalogue.** They are ordinary
  Library versions, so projects, version switching and saving work fully
  offline. A version removed or yanked from the catalogue keeps working
  where it is installed.
- An artifact download that fails leaves nothing behind: the staging folder
  is removed and the Library is unchanged.

## 9. P4.3.1 implementation plan: read-only fetch and safe install

Scope: get the catalogue, show it minimally, and install one exact version.
There is still no submission tooling and no runtime capability gate.

1. **Configuration.** One built-in `CatalogueSource` (owner and repo to be
   decided) with an override in settings for testing. HTTPS client from
   the existing `reqwest` (blocking, on a worker thread) with connect and
   read timeouts, no redirects outside `raw.githubusercontent.com`, and
   streaming with hard byte caps.
2. **Catalogue fetch and cache** (`marketplace/cache.rs`): fetch
   `index.json` from the configured branch, enforce `MAX_CATALOGUE_BYTES`
   while streaming, `parse_catalogue`, `check_refresh` against the cache,
   atomic cache write. Use the outcomes table in §8. Tests use a local
   fake fetcher (trait) for offline, invalid, rollback and rewrite cases.
3. **`.pwpkg` parsing** (`marketplace/artifact.rs`): stream-download with
   a cap of `min(declared size, MAX_ARTIFACT_BYTES)`. Require exact size
   and SHA-256 before parsing. Parse the envelope (format, id, version
   must match), run `check_artifact_listing`, enforce the per-file limit,
   and require UTF-8.
4. **Capability scanner** (`marketplace/capabilities.rs`): an allowlist
   classification of every node type in every `.pwnode` (root plus deps),
   failing closed for unclassified types. Rejects `native_code`. Requires
   declared ⊇ detected. Unit tests per node family.
5. **Install** (`marketplace/install.rs`):
   - write files into `packages/.staging-<rand>/`;
   - `check_manifest_matches`, `verify_version_dir(staging, false)`, then
     the capability scan;
   - refuse an existing different version folder (identical means already
     installed);
   - rename into `packages/<id>/<version>/` and invalidate the Library
     cache.

   Reuse the publish staging and cleanup code. Failure-injection tests at
   every step (like `FailPoint` in Stage 4).
6. **Minimal UI:** a Marketplace panel with search by id, name and tag, a
   package detail view (id, publisher namespace, versions with
   compatibility and yanked state, capabilities, documentation link), and
   an "Install <version>" button with the capability consent dialog.
   Inserting an installed node uses the existing Library insertion.
7. **Tests:** offline and refresh outcomes, size-cap aborts, digest
   mismatch, malicious envelopes (traversal, extra files, duplicates,
   non-UTF-8), install atomicity, no overwrite of existing or local
   packages, and an installed package resolving, bundling into a project
   and reopening offline.

**Later stages:** P4.3.2 adds runtime capability grants and the
"Updates available" display (still no automatic upgrade). P4.3.3 adds the
catalogue repository's CI validator binary (sharing this module) and the
submission guide.
